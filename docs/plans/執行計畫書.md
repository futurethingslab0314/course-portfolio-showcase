# FieldMapping 可學習化執行計畫書

版本：v1  
日期：2026-02-28

## 1. 目標

1. 新的 Source Database 在做 `field -> category` 分析時，可參考歷史 mapping 與人工修正結果。
2. 保留 Notion 手動調整的決策，不被自動推論覆蓋。
3. 建立單一真相來源（SSOT），降低規則重複與文件衝突。

## 2. 可直接通用的既有文件

以下文件維持為現有主體，後續新增文件應以「引用」為主，不重寫同一規則。

1. `docs/source-database-schema-guideline.md`  
   用途：欄位命名原則、UiPattern 訊號、FieldMapping 推論重點。
2. `docs/notion-data-contract.md`  
   用途：Canonical mapping、enum lock、fallback 與可靠性原則。
3. `docs/ui-pattern-json-spec.md`  
   用途：FieldMapping 對接格式與 pattern 欄位最低要求。
4. `skills/notion-ui-mapper/SKILL.md`  
   用途：既有 skill workflow 與輸出要求。
5. `skills/notion-ui-mapper/references/notion-schema-rules.md`  
   用途：Notion schema 與 FieldMapping 基本規則。
6. `skills/notion-ui-mapper/references/mapping-examples.md`  
   用途：FieldMapping JSON / line-based 範例。

## 3. 需新增的文件（最小可行集合）

1. `docs/fieldmapping-ssot-policy.md`  
   目的：定義權威來源與衝突時優先序。
2. `docs/fieldmapping-review-thresholds.md`  
   目的：定義 confidence 門檻與人工覆核條件。
3. `skills/notion-ui-mapper/references/field-alias-dictionary.md`  
   目的：集中管理跨 DB 同義詞與負向規則（避免誤配）。
4. `skills/notion-ui-mapper/references/historical-mapping-guide.md`  
   目的：定義如何利用歷史 mapping（同 DB 與跨 DB）。
5. `skills/notion-ui-mapper/references/conflict-resolution-rules.md`  
   目的：多來源規則互撞時的裁決順序與記錄方式。

## 4. SSOT 與衝突處理原則

優先順序（由高到低）：

1. Notion 人工最終修正（latest `updated_at`）
2. 同 `sourceDatabaseId` 的歷史 mapping
3. 跨 DB alias / pattern 規則
4. 關鍵字推論與 fallback

規則：

1. 不在多份文件重複維護同一組 synonym。
2. 發生衝突時，只在 SSOT 文件修正；其他文件改為引用。
3. 所有低信心對應需進入 `needs_review`，不自動定稿。

## 5. 執行階段與交付物

### Phase A：盤點與去重（1-2 天）

任務：

1. 盤點現有 docs/skill references 的重複規則。
2. 標記每條規則的權威文件來源。

交付物：

1. `fieldmapping-ssot-policy.md` 初版（含來源對照表）。

### Phase B：建立可重用字典（1-2 天）

任務：

1. 整理常見欄位同義詞（例如 `AssignmentName/Title/ProjectName/Name`）。
2. 定義負向規則（例如 `assignmentName` 不可對到 `StudentName`）。

交付物：

1. `field-alias-dictionary.md` 初版。

### Phase C：歷史映射策略落地（1 天）

任務：

1. 定義同 DB 優先、跨 DB 次要的重用策略。
2. 定義歷史版本挑選策略（以最新有效版本為準）。

交付物：

1. `historical-mapping-guide.md`。

### Phase D：人工覆核機制（0.5-1 天）

任務：

1. 設定 confidence 門檻（高/中/低）。
2. 定義 review 清單輸出欄位與處理流程。

交付物：

1. `fieldmapping-review-thresholds.md`。

### Phase E：Skill 文件整合（0.5-1 天）

任務：

1. 將新增 references 掛到 `skills/notion-ui-mapper/SKILL.md` workflow。
2. 調整說明為「先讀 SSOT，再做推論，再輸出 review」。

交付物：

1. 更新後的 `SKILL.md`（僅流程說明，不改 UI 邏輯）。

## 6. 驗收標準

1. 新 Source Database 可在一次流程內產出可用 FieldMapping。
2. 同一規則只在一份權威文件維護，不再多處矛盾。
3. 低信心欄位都被標記 `needs_review`。
4. Notion 手動修正可在下一輪分析被參考。

## 7. 風險與緩解

1. 風險：同義詞過度擴張造成誤配。  
   緩解：加入 negative rules 與人工覆核門檻。
2. 風險：歷史 mapping 帶入過時規則。  
   緩解：以 `updated_at` + 版本策略淘汰舊規則。
3. 風險：文件持續分叉。  
   緩解：任何規則修改都先更新 SSOT，再同步引用。

## 8. 操作 SOP（每次同步循環）

1. Sync Notion 最新 FieldMapping 修正。
2. 以 SSOT + 歷史 mapping 分析新資料庫欄位。
3. 輸出建議 mapping 與 review 清單。
4. 人工覆核後回寫 Notion。
5. 下次分析重用更新後規則。
